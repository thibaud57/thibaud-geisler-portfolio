## Phase 2 — Faux positif : métadonnées streamées sur `/projets/[slug]`

> **Requalifié après vérification.** Le premier passage de cet audit a conclu à un problème structurel. La méthode de crawl était en cause, pas le site. Le constat brut ci-dessous reste exact, son interprétation initiale était fausse.

**Le constat brut** : crawlée avec un user-agent anonyme (`curl`), `/fr/projets/portfolio` renvoie un `<head>` sans `<title>`, `<meta description>`, `og:*` ni canonical. Le vrai `<title>` existe, mais à l'octet 12 421, après la fermeture de `</head>` à l'octet 3 317.

**Ce que ça n'est pas** : un défaut de rendu. C'est le [streaming metadata](https://nextjs.org/docs/app/api-reference/functions/generate-metadata#streaming-metadata) de Next 15.2+, actif par défaut sur les pages non prérendues. Next sert un rendu **bloquant** aux user-agents matchant [`htmlLimitedBots`](https://nextjs.org/docs/app/api-reference/config/next-config-js/htmlLimitedBots), dont la liste par défaut couvre justement les crawlers d'aperçu de partage.

**Vérification par user-agent**, même URL, même déploiement (`v1.6.1`, avant tout correctif) :

| User-agent | `</head>` | `<title>` | Verdict |
|---|---|---|---|
| `curl/8` | 3 317 | 12 421 | streamé, hors `<head>` |
| `Googlebot` | 3 317 | 12 421 | streamé, hors `<head>` |
| `LinkedInBot` | 6 644 | 3 598 | dans le `<head>` |
| `Twitterbot` | 6 644 | 3 598 | dans le `<head>` |
| `facebookexternalhit` | 6 644 | 3 598 | dans le `<head>` |
| `Slackbot` | 6 644 | 3 598 | dans le `<head>` |
| `bingbot` | 6 644 | 3 598 | dans le `<head>` |

Les aperçus LinkedIn, Twitter/X, Slack et Facebook n'ont donc jamais été cassés. Googlebot reste volontairement en streaming, il exécute le JS, ce que confirme le Rich Results Test en Phase 3.

**Le risque résiduel, réel mais étroit** : les crawlers HTML-only absents de la liste par défaut. Telegram, iMessage, Bluesky et Mastodon n'y figurent pas et reçoivent le comportement observé avec `curl`.

**Correctif retenu** : `generateStaticParams()` sur `src/app/[locale]/(public)/projets/[slug]/page.tsx`, retournant les 11 slugs publiés × 2 locales. Les 22 pages sont prérendues au build, métadonnées figées dans le `<head>` pour tous les user-agents. Vérifié sur un build local : `<title>` à l'octet 3 640 pour un `</head>` à 6 871, identique pour `curl` et Googlebot. Bénéfice principal en réalité : premier hit instantané, plus la couverture des crawlers hors liste. La justification par les aperçus sociaux cassés était erronée.

**Note de build** : une erreur `"use cache" cannot be used outside of App Router. Expected a WorkStore` est apparue une fois lors de la collecte de page data de cette route, puis ne s'est plus reproduite sur 5 builds dont 3 avec `.next` supprimé.

Le pattern en cause est pourtant celui que Next documente : `generateStaticParams` reste une fonction ordinaire qui appelle un helper marqué `'use cache'`, jamais l'inverse. Le guide de migration l'écrit pour les route handlers, *« The directive can't be applied to the `GET` export itself, so the handler calls a cached helper »*, et `sitemap.ts` suit déjà la même forme avec la même query.

L'erreur relève donc d'un bug d'infrastructure et non du code. Elle appartient à la famille des pertes de contexte `AsyncLocalStorage` sous Turbopack, dont un cas voisin est documenté en [discussion #86978](https://github.com/vercel/next.js/discussions/86978) : un mainteneur y décrit une course entre l'abandon du prérendu et la reprise de stream sous charge processeur, qui fait perdre son contexte à des pages au hasard. Aucune issue ne porte la signature exacte rencontrée ici, le rapprochement reste une analogie.

**Conduite retenue** : surveillance, pas de changement préventif. Passer à une query non cachée n'éliminerait pas la cause et ferait perdre le cache partagé avec le sitemap. Si l'erreur revient, garder le log complet et ouvrir une issue chez Next en citant la discussion ci-dessus.

**Écarté** : désactiver le streaming globalement via `htmlLimitedBots: /.*/`. Bugs connus avec `cacheComponents` + PPR sur 16.2.x-16.3.0 ([#96593](https://github.com/vercel/next.js/issues/96593), [#95406](https://github.com/vercel/next.js/issues/95406)). Désactiver `cacheComponents` a également été écarté, la doc Next 16 étiquette l'ancien modèle « Caching (Previous Model) » et toute la stack du projet repose sur `'use cache'`.

## Phase 5 — Soft 404 sur `/projets/[slug]` : comportement attendu, impact limité

Un slug inexistant renvoie **HTTP 200** au lieu de 404, en production comme en local, avant comme après `generateStaticParams`.

| URL testée | Contexte | Code |
|---|---|---|
| `/fr/projets/slug-bidon-xyz` | prod `v1.6.1` | 200 |
| `/fr/projets/slug-bidon-xyz` | prod, UA `LinkedInBot` | 200 |
| `/fr/projets/slug-bidon-xyz` | standalone local, comme la prod Docker | 200 |
| `/fr/projets/slug-bidon-xyz` | `next dev` | 200 |
| `/fr/page-inexistante` (hors segment dynamique) | standalone local | 404 |

**Ce n'est pas un bug, c'est documenté.** Next l'écrit noir sur blanc : *« Along with serving a custom UI, Next.js will return a `200` HTTP status code for streamed responses, and `404` for non-streamed responses »* ([not-found.js](https://nextjs.org/docs/app/api-reference/file-conventions/not-found)). Les en-têtes partent avec le shell, avant que `notFound()` ne s'exécute dans le composant streamé, et un statut déjà envoyé ne se réécrit pas. Avec `cacheComponents`, toute route dynamique streame un shell d'abord, donc le cas est systématique.

**La mitigation officielle est en place et vérifiée.** Next injecte `noindex` dans le HTML de ces réponses, ce qui empêche l'indexation malgré le 200. Vérifié en production :

```
/fr/projets/slug-bidon-xyz   →  <meta name="robots" content="noindex"/>
/fr/projets/portfolio        →  aucune balise robots
```

La doc le confirme : *« Some crawlers may label these responses as "soft 404s". In the streaming case, this does not lead to indexation because the page is explicitly marked `noindex` in the HTML »* ([loading.js § Status Codes](https://nextjs.org/docs/app/api-reference/file-conventions/loading#status-codes)).

**Impact résiduel** : du bruit dans le rapport « Soft 404 » de Search Console, et un peu de budget de crawl sur des URL ni indexées ni proprement supprimées. Pas de pénalité de classement, pas d'indexation parasite.

### Pistes écartées, testées

- **`notFound()` plus tôt, dans le composant de page** : testé sur un build local, statut toujours 200. Le shell est déjà parti. Next demande de placer la vérification avant toute frontière de suspension, ce que `cacheComponents` rend impossible dans la page.
- **`dynamicParams = false`** : casse le build, `Route segment config "dynamicParams" is not compatible with nextConfig.cacheComponents`. La règle projet qui le recommandait a été corrigée.
- **`not-found.tsx` au niveau du segment** : change l'interface affichée, jamais le statut HTTP.
- **`notFound()` dans `generateMetadata`** : sous `cacheComponents`, la fonction est elle aussi reportée au moment de la requête pour un slug non prérendu. Même limite.

### Seule voie officielle si on veut le vrai 404

Faire la vérification dans `src/proxy.ts`, avant le streaming : *« With Cache Components, every dynamic route streams a static shell first, so run that check in `proxy` instead »* ([notFound()](https://nextjs.org/docs/app/api-reference/functions/not-found)). Depuis Next 16 le proxy tourne en runtime Node, donc Prisma y est techniquement possible.

**Non appliqué**, deux raisons. La règle `.claude/rules/nextjs/proxy.md` interdit les appels base de données dans le proxy, qui est traversé par chaque requête. Et le gain réel se limite à du confort de reporting, puisque le `noindex` couvre déjà l'enjeu d'indexation. À rouvrir si le rapport Search Console devient gênant, avec une liste de slugs en mémoire plutôt qu'une requête par visite.
